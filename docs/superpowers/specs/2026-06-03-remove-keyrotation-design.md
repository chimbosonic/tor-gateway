# Remove `TorServicePolicy.keyRotation` (design)

Delete `KeyRotationSpec` and the `TorServicePolicySpec.KeyRotation` field from `policy.torgateway.io/v1alpha1`. The fields are unimplemented and their semantics fit neither of the two real use cases for hidden-service key rotation. Keeping them invites users to set knobs that do nothing.

## Why deletion, not implementation

A v3 `.onion` address *is* the ed25519 public key. Any rotation produces a new published address; "rotation with overlap" only works by serving multiple `HiddenServiceDir` stanzas, which is a different design than the current `RetainPreviousKeys: 0–10` field implies (it just retains keys *in the Secret*).

The two legitimate use cases for rotating a hidden-service key are:

1. **Pseudonymity churn** — periodically cycle the published `.onion` so past activity does not trivially link to current. Wants a clean cut. A grace window defeats the purpose.
2. **Compromise repudiation** — the legitimate operator disowns a leaked key. Wants the compromised key out *now*, also a clean cut. Trigger is event-driven, not scheduled.

Neither benefits from `RetainPreviousKeys`. `Schedule` (cron) only fits (1); (2) needs a separate trigger we have not designed. The current `KeyRotationSpec` cannot serve either use case correctly without further design work, and the right time to revisit is alongside onionbalance HA (where retaining keys *as serving instances* becomes meaningful — see [Future work](#future-work)).

The operator is `v0.x` alpha with no controller logic behind the fields and no users depending on observed behavior. This is the cheapest moment to remove them.

## API compatibility

The CRD group is `policy.torgateway.io/v1alpha1` and the project is pre-`v1.0.0`. No API stability is promised. The behavioral risk is zero (the fields are inert today). The only user-visible breakage is that an existing `TorServicePolicy` manifest containing `spec.keyRotation:` will fail `kubectl apply` against the new CRD because the field is unknown. We accept that — the field has never done anything at runtime, so no running deployment changes behavior.

No conversion webhook, no deprecation period.

## Future work

If pseudonymity churn or compromise repudiation becomes a real requirement later, design from scratch rather than reviving these fields:

- **Pseudonymity churn**: a separate `TorKeyRotation` resource (or a `keyEpoch` int on the policy) that triggers a clean cut. No `RetainPreviousKeys`. Scheduled rotation worth implementing only when the user actually wants their `.onion` to change on a cadence.
- **Compromise repudiation**: same trigger mechanism, manually invoked. Pairs with a recorded `previous-onion` annotation for audit.
- **Multi-instance key handling**: only meaningful once onionbalance HA lands. Backend instance keys can rotate without changing the user-visible master `.onion`; that is the only "retain previous keys" semantic that actually makes sense, and it lives entirely inside the onionbalance design.
