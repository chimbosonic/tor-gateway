# v0.3.1 ops fixes — design

Two bundled operational fixes for a patch release:

1. **Events RBAC** — the operator's `EventRecorder` calls silently fail on a strict cluster because the generated `Role` lacks `events: create;patch`.
2. **Data-plane probes** — the per-Gateway Tor Deployment has no liveness/readiness probes on either container. The router binds loopback only, so kubelet cannot probe it directly without a dedicated health listener. Tor exposes no probeable port until `MetricsPort` is enabled.

Out of scope (kept on the follow-ups list): NetworkPolicy implementation, `retainPreviousKeys` dead field cleanup, Tor `ClientOnionAuthDir` ownership gotcha docs.

## Why these together

Both are small, both are "the operator does the right thing under normal load but degrades silently when something goes wrong." Bundling avoids two patch releases for ~150 lines of change.

## 1. Events RBAC

### Problem

`internal/controller/*.go` reconcilers record events via the shared `EventRecorder` (vanity harvest progress, policy validation failures, etc.). On a cluster with a default-deny RBAC posture, those `Events.Create` calls return Forbidden, the recorder logs a warning, and the user loses the diagnostic surface they would otherwise see in `kubectl describe gateway`.

### Change

Add one kubebuilder marker to the Gateway reconciler:

```go
// +kubebuilder:rbac:groups="",resources=events,verbs=create;patch
```

Kubebuilder aggregates markers across the codebase into the single `config/rbac/role.yaml`, so the marker only needs to live in one reconciler file. Place it next to the existing `secrets`/`configmaps` markers in `internal/controller/gateway_controller.go`.

Regen:

- `make manifests` → updated `config/rbac/role.yaml`.
- `make chart-sync` → mirrors the role into `charts/tor-gateway/files/rbac/manager-role-rules.yaml` (consumed by the chart's `templates/clusterrole.yaml` wrapper).

### Test

Unit test that loads `config/rbac/role.yaml` (parse as YAML, look at `rules`) and asserts a rule exists with:

- `apiGroups: [""]`
- `resources` contains `"events"`
- `verbs` contains both `"create"` and `"patch"`

Cheap, mechanical, and catches regressions if a future generator change drops the marker.

## 2. Router probes

### Problem

The router serves traffic on `127.0.0.1:9080` — intentional, so only the in-pod Tor can reach it. Kubelet probes the pod IP, not loopback, so it cannot `httpGet` or `tcpSocket` the traffic port. With no probe today, kubelet only catches a crashed router (process exit → container restart). A wedged-but-running router is invisible.

The router image is `gcr.io/distroless/static:nonroot` (no shell, no curl), so an `exec` probe is not viable.

### Change

Add a second, narrow HTTP listener on the router for kubelet-only health checks:

- `cmd/router/main.go`:
  - New flag `--probe-addr` (default `:8081`).
  - Start a second `http.Server` after the route aggregator has loaded its initial rule set.
  - One handler: `GET /healthz` → `200 OK`. No body content required.
  - The probe server starts **after** initial rule load, so readiness signals "rules loaded and listener up" rather than just "process exists."

- `internal/controller/gateway_resources.go`:
  - Add `containerPort: 8081` (name `probe`) to the router container.
  - Add `livenessProbe` and `readinessProbe` (`httpGet` `/healthz` on `8081`):
    - `initialDelaySeconds: 5`, `periodSeconds: 10`, `timeoutSeconds: 2`, `failureThreshold: 3`.

The probe port is **not** exposed via any Service — it's a kubelet-only signal. Only declared as a `containerPort` so kubelet can target it on the pod IP.

### Tests

- Unit test the `/healthz` handler via `net/http/httptest`: returns 200, no body required.
- Extend `gateway_resources_test.go`: assert `BuildDeployment` renders the probe port and both probes on the router container with the specified fields.

Existing real-Tor e2e specs (`dataplane_test.go`, `dataplane_crossns_test.go`, `vanity_test.go`, `clientauth_test.go`) implicitly cover the integration: pods must reach `Ready` before any of those tests can route traffic. If readiness regresses, those specs fail.

## 3. Tor probes (MetricsPort)

### Problem

Tor today binds no probeable port — only the `HiddenServicePort` target, which is loopback. An `exec` probe on busybox (`pidof tor`) catches process death but not a wedged tor (e.g. circuit-build failure loop, descriptor publish failure). Container-restart-on-exit handles crashes but nothing else.

### Change

Enable Tor's `MetricsPort` (Prometheus exposition format, exposed by `tor` itself at the HTTP root) and probe it via `httpGet`.

`internal/tor/torrc.go`:

- Add two config fields:
  - `MetricsPort int` (default `9035`).
  - `MetricsPortPolicy string` (default `accept 0.0.0.0/0`).
- Render:

  ```
  MetricsPort 0.0.0.0:9035
  MetricsPortPolicy accept 0.0.0.0/0
  ```

`internal/controller/gateway_resources.go`:

- Add `containerPort: 9035` (name `metrics`) to the tor container.
- Add three probes (all `httpGet` `/metrics` on `9035`):
  - **startupProbe**: `failureThreshold: 30`, `periodSeconds: 5` — up to ~2.5 min for tor bootstrap before kubelet considers startup failed. Startup probe gates the other two.
  - **livenessProbe**: `periodSeconds: 10`, `timeoutSeconds: 2`, `failureThreshold: 3`.
  - **readinessProbe**: `periodSeconds: 10`, `timeoutSeconds: 2`, `failureThreshold: 3`.

### Security note

`MetricsPort` exposes Tor counters (circuits built, descriptors published, bandwidth) but **no** key material and **no** descriptor content. It is reachable from anywhere in-cluster on the pod IP. This is acceptable for now because:

- The metrics are not directly sensitive.
- A NetworkPolicy (separate follow-up) will scope ingress to kubelet only once implemented.

Document this exposure in the spec and bump the NetworkPolicy follow-up priority: adding `MetricsPort` is what makes the NetworkPolicy gap actually load-bearing.

### Tests

- `internal/tor/torrc_test.go`: extend an existing render test (or add a focused one) asserting the rendered torrc contains `MetricsPort 0.0.0.0:9035` and `MetricsPortPolicy accept 0.0.0.0/0` when the config has the default values.
- `gateway_resources_test.go`: assert `BuildDeployment` renders the metrics container port and all three probes on the tor container.

Real-Tor e2e covers the integration (tor must reach `Ready` before any HS traffic flows).

## Release

After merge, cut `v0.3.1` (patch). CI auto-versions `Chart.yaml` from the tag, same as v0.3.0.

## Decisions / non-choices

- **Single `/healthz` for router liveness AND readiness.** Splitting them adds complexity without value here — the router has no half-ready state worth distinguishing.
- **Tor MetricsPort bound to `0.0.0.0`, not loopback.** Loopback would defeat the purpose; kubelet cannot reach loopback.
- **`MetricsPortPolicy accept 0.0.0.0/0`** rather than per-IP. Tor's policy syntax does not match arbitrary pod IPs cleanly, and a NetworkPolicy is the right place to scope ingress, not the metrics policy.
- **`startupProbe` only on tor, not router.** The router starts in milliseconds; a startupProbe would just be extra noise.

## Risks

- **Old torrc consumers**: the new `MetricsPort` fields are additive with defaults — existing callers in tests and the gateway controller get the metrics port automatically. Unit tests will catch any breakage in render output.
- **Probe port collision**: `8081` (router probe) and `9035` (tor metrics) are picked to avoid the existing `9080` (router traffic) and `9050`/`9051` (Tor SOCKS/control if ever enabled). No known conflicts.
- **NetworkPolicy lag**: until NetworkPolicy ships, the metrics endpoint is in-cluster-reachable. Documented above; not a regression (today there is no NetworkPolicy gating anything in this pod).
